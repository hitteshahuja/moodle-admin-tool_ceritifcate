DIVERGENCE FROM UPSTREAM — admin/tool/certificate
===================================================

Upstream reference: Moodle Workplace tool_certificate plugin
Repository:         https://github.com/moodlehq/moodle-tool_certificate (or equivalent Moodle HQ source)
Maintained fork:    https://github.com/hitteshahuja/moodle-admin-tool_ceritifcate

This file documents every intentional departure from the upstream plugin.
Any merge from upstream must be reconciled against these changes.


1. NEW ELEMENT — element/incrementingnumber
-------------------------------------------
Type: Addition (new certificate element subplugin)
Files added:
  element/incrementingnumber/
    classes/element.php
    lang/en/certificateelement_incrementingnumber.php
    tests/element_test.php
    phpunit.xml
    version.php

Description:
  A certificate element that prints an automatically incrementing sequential
  number on each issued certificate.  The starting value is configurable per
  element instance (default: 1).  The number is generated on first render and
  stored in tool_certificate_issues.data as JSON key
  "incrementingnumber_<element_id>".

  Number-generation logic (element.php::render()):
    next = max( (start-1) + activeCount + 1,  lastAssigned + 1,  start )
  where activeCount excludes soft-deleted (revoked) rows — see change 2.


2. SOFT-DELETE ON REVOKE (to prevent certificate number reuse)
--------------------------------------------------------------
Type: Behaviour change + schema addition
Affected files:
  db/install.xml
  db/upgrade.php          (new step 2026042601)
  version.php             (2026042600 → 2026042601)
  classes/template.php    (revoke_issue, revoke_issues, issue_certificate)
  element/incrementingnumber/classes/element.php (get_element_issue_count)
  classes/reportbuilder/local/entities/issue.php (status column)
  classes/reportbuilder/local/formatters/certificate.php (status formatter)
  lang/en/tool_certificate.php ($string['revoked'])

Problem fixed:
  The upstream plugin hard-deletes the row from tool_certificate_issues when
  a certificate is revoked.  When an incrementingnumber element calculates the
  next number to assign it uses:
    (a) COUNT of existing rows for that element   — decreases after hard-delete
    (b) MAX number already assigned               — decreases after hard-delete
  Both counters can fall below the number that was on the revoked certificate,
  causing a newly issued certificate to receive a number that was already
  printed on a previously revoked certificate.

Changes made:

  2a. New DB column: tool_certificate_issues.revoked (INT 1, DEFAULT 0)
      Revoked issues are kept in the table with revoked=1.  This is the
      source-of-truth that a number has been consumed and must not be reused.

  2b. template.php::revoke_issue()
      Changed from:  $DB->delete_records('tool_certificate_issues', ['id' => $issueid])
      Changed to:    $DB->set_field('tool_certificate_issues', 'revoked', 1, ['id' => $issueid])
      The PDF file and custom-field data are still deleted; only the bare row
      (with its stored incrementing number) is kept.

  2c. template.php::revoke_issues()   [template-deletion path]
      Intentionally still performs a hard-delete.  When the whole template is
      deleted the element definitions are also deleted, so there is no element
      left that could ever assign a new number from that template.  Keeping
      the rows would be dead weight.  This method now inlines the cleanup
      logic directly rather than delegating to revoke_issue().

  2d. template.php::issue_certificate()
      Added explicit   $issue->revoked = 0;
      on the new-issue object to satisfy Moodle's event-snapshot field
      validator, which requires every column to be present in the snapshot.

  2e. element.php::get_element_issue_count()
      Added   AND revoked = 0
      to the COUNT query so that soft-deleted rows are not counted as active
      issues.  The companion method get_last_issued_number() is intentionally
      left unchanged — it must see revoked rows so the max-number guard can
      prevent reuse.

  2f. Report builder — status column
      Added ->add_field("{$alias}.revoked") to the status column definition
      and updated the formatter callback to return get_string('revoked', ...)
      when revoked = 1, taking precedence over the expired/valid check.

  2g. Lang string
      Added:  $string['revoked'] = 'Revoked';


3. UNIT TESTS
-------------
Type: Addition / update
Affected files:
  element/incrementingnumber/tests/element_test.php
  tests/template_test.php
  tests/external_test.php

New tests added (element_test.php):
  test_revoke_does_not_reuse_number
    — Revoking the most-recently-issued certificate must not allow its
      assigned number to be issued again.
  test_revoke_all_numbers_no_reuse
    — After revoking every certificate for a template the next issue must
      continue from lastAssigned+1, not restart from the start number.
  test_revoke_middle_number_no_reuse
    — Revoking a certificate in the middle of the sequence must leave a gap;
      the gap must never be backfilled.

Existing tests updated:
  template_test.php::test_revoke_issue
    — Updated assertions to expect the row to remain (revoked=1) rather than
      to disappear from the table.
  external_test.php::test_delete_issue
    — Updated get_records() call to filter on revoked=0 when checking which
      active issues remain after a revoke.
  element_test.php::test_incrementing_numbers_with_deletion
    — Changed from direct $DB->delete_records() to certificate->revoke_issue()
      so the test exercises the real soft-delete path.
  element_test.php::setUp()
    — Added require_once($CFG->libdir.'/pdflib.php') so tests that use \pdf
      work correctly when run in isolation via a PHPUnit filter.


4. PDF LOCKDOWN ON REVOKE
-------------------------
Type: Behaviour change (bug fix) + version bump. No schema change.
Affected files:
  classes/template.php                                  (create_issue_file, get_issue_file)
  lib.php                                                (tool_certificate_pluginfile — 'issues' filearea)
  view.php
  classes/external/issues.php                            (regenerate_issue_file)
  classes/reportbuilder/local/systemreports/issues.php    (View / Regenerate file row actions)
  classes/certificate.php                                 (get_issues_for_user)
  classes/my_certificates_table.php                       (col_download)
  version.php                                             (2026071300 → 2026071301)
  tests/template_test.php, tests/external_test.php, tests/my_certificates_table_test.php
Also affected (separate repository, not yet a submodule of this checkout):
  mod/coursecertificate/classes/output/mobile.php

Problem fixed:
  revoke_issue() already soft-deletes the issue row (revoked=1, per change 2)
  and deletes the stored PDF, but nothing stopped the PDF being silently
  regenerated afterwards. get_issue_file()/get_issue_file_url() recreate the
  file on demand whenever it is missing, and that ran every time someone
  opened view.php?code=..., the mobile app certificate view, or clicked the
  "Regenerate file" action in the admin issues report — even for a revoked
  issue. In practice, revoking a certificate never actually stopped it being
  downloaded; only the issue row's revoked flag changed.

Changes made:

  4a. template.php::create_issue_file() / get_issue_file()
      Both now throw moodle_exception('certificaterevoked', 'tool_certificate')
      immediately if $issue->revoked is set, instead of generating/returning
      a PDF. This is the single choke point every other call path goes
      through, so it protects all callers, including third-party code
      (mod_coursecertificate, local_mmt_utilities) that calls these methods
      directly.

  4b. lib.php::tool_certificate_pluginfile() — 'issues' filearea
      Added `if ($issue->revoked) return false;` before the file lookup, as
      defence-in-depth in case a stored file is ever left behind for a
      revoked issue.

  4c. view.php
      Now checks $issue->revoked before calling get_issue_file_url() and
      throws moodle_exception('certificaterevoked', ...) with a clear
      message instead of redirecting to a (regenerated) PDF.

  4d. classes/external/issues.php::regenerate_issue_file()
      The "Regenerate file" web service now rejects revoked issues before
      calling create_issue_file(), failing fast with a clear WS error
      rather than relying on the exception from 4a.

  4e. classes/reportbuilder/local/systemreports/issues.php
      The "View" and "Regenerate file" row actions in the admin issues
      report are now hidden for revoked rows (!$row->revoked), matching the
      existing behaviour of the "Revoke" action. Added `revoked` to
      $requiredcolumns so the callbacks have the data they need.

  4f. classes/certificate.php::get_issues_for_user()
      Added ci.revoked to the SELECT so the "My certificates" table can
      distinguish revoked issues from active ones.

  4g. classes/my_certificates_table.php::col_download()
      Renders a "Revoked" badge instead of the download/view icon when the
      issue is revoked. The row itself is NOT removed from the list — the
      issue entry, code and dates stay visible; only the PDF link is gone.

  4h. mod_coursecertificate/classes/output/mobile.php (separate repository)
      The mobile app "studentview" no longer requests a file URL for a
      revoked issue (empty($issue->revoked) added to the condition),
      avoiding an uncaught exception from 4a on that code path.

  4i. version.php
      2026071300 → 2026071301. No new DB field or upgrade step — this is a
      pure behaviour/version bump so admins and hosting providers can see
      the plugin changed and Moodle purges caches on upgrade.

  4j. Tests
      New:
        tests/template_test.php::test_get_issue_file_revoked
        tests/template_test.php::test_create_issue_file_revoked
        tests/external_test.php::test_regenerate_issue_file_revoked
        tests/my_certificates_table_test.php::test_col_download
      Confirmed still passing: the rest of template_test.php, external_test.php,
      my_certificates_table_test.php, certificate_test.php, and
      mod_coursecertificate/tests/helper_test.php.

  See DEPLOYMENT_AND_TEST_PLAN.md for the hosting-provider deployment and
  QA checklist for this change.
